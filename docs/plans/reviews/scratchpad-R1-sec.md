## Резюме

Блокирующих находок нет. Есть одна важная: `move_window_to_space` не проверяет, что у приватного класса SkyLight есть нужные селекторы. Если в другой версии macOS их не окажется, процесс Glide аварийно завершится. Сейчас функцию вызывает только devtool, поэтому исправить нужно до того, как её подключит T6. Запуск `open -b` безопасен: shell не используется, id проверяется, а приложение запускает LaunchServices, поэтому права Glide ему не достаются.

**Вердикт:** волну можно мержить. S1 нужно закрыть до T6 (в F1 или в самой T6).

## Находки

### S1. `move_window_to_space` вызывает селекторы приватного класса без проверки их наличия

- **Серьёзность:** важная
- **Где:** `src/sys/space_move.rs:32-47`
- **Класс:** отказ в обслуживании из-за непроверенного FFI (CWE-248, неперехваченное исключение)
- **Кто может:** специально никто. Сработает само, если на какой-то версии macOS класс `SLSBridgedMoveWindowsToManagedSpaceOperation` есть, а `-initWithWindows:spaceID:` или `-performWithWMBridgeDelegate` отсутствует или имеет другую сигнатуру. Это приватный API, который появился в macOS 26 и может меняться
- **Путь:** (в будущем, T6) команда Reactor → `move_window_to_space` → `AnyClass::get` проверяет только класс → `msg_send![.., initWithWindows:spaceID:]` / `performWithWMBridgeDelegate`
- **Чем грозит:** Glide падает целиком, и все окна остаются без управления.
  - В release-сборке objc2 сигнатуры не проверяет. Неизвестный селектор бросает `NSException`, та раскручивается через `objc_msgSend` (ABI `C-unwind`) в Rust-код, и процесс аварийно завершается. Кроме того, в `Cargo.toml:32` стоит `release.panic = "abort"`, а feature `catch-all` у objc2 не включена.
  - В debug-сборке objc2 0.6.3 проверяет сигнатуру (`msg_send_check_class` в `objc2/src/runtime/message_receiver.rs`) и при расхождении паникует в потоке вызывающего.
- **Что уже хорошо:** по отчёту T3 живая проверка шла через `devtool space move-window`. Для `cargo run --example` по умолчанию собирается debug-сборка, а в ней objc2 сверяет кодировки, так что на macOS 27 типы (`NSArray`, `u64`, `void`), скорее всего, указаны верно. Сборку, которой проверял T3, я не видел. Если `init` вернул nil, функция возвращает `Unsupported`. Владение объектами корректно: `alloc` → `init` передаёт владение в `Option<Retained<_>>`, после `perform` объект освобождается, а `NSArray::from_retained_slice` удерживает свои элементы. Падающий синхронный вариант `performSynchronousBridgedWindowManagementOperation:` в коде не используется: `grep` по `src` и `examples` его не находит.
- **Как чинить:** перед `alloc` проверить оба селектора через `AnyClass::verify_sel` из objc2 0.6: `cls.verify_sel::<(&NSArray<NSNumber>, u64), Option<Retained<AnyObject>>>(sel!(initWithWindows:spaceID:))` и `cls.verify_sel::<(), ()>(sel!(performWithWMBridgeDelegate))`. Точные типы параметров подобрать так, чтобы `verify_sel` компилировался. При ошибке возвращать `SpaceMoveError::Unsupported`. Результат проверки можно закешировать (`OnceLock`), чтобы не искать методы при каждом вызове.
- **Как проверить:** добавить unit-тест, который вызывает функцию проверки с несуществующим селектором на существующем классе (например `NSObject`) и получает `Err`, а не панику. `devtool space move-window` на своём окне TextEdit работает как раньше.

### S2. Правила окон из IPC `UpdateConfig` не проходят новую валидацию

- **Серьёзность:** замечание
- **Где:** `src/actor/server.rs:25,100`, `src/config.rs:59-64` (`Config` выводит `Deserialize`), `src/config.rs:175-191,385-396` (валидация только в `ConfigPartial::validate`)
- **Кто может:** локальный процесс того же пользователя, отправляющий сообщение в CFMessagePort Glide
- **Путь:** `Request::UpdateConfig(Config)` → `ron::de::from_bytes` → `WmEvent::ConfigUpdated`. `WindowRule::validated` и `FractionalRect::validated` на этом пути не вызываются. Штатный CLI (`src/bin/glide.rs:138-145`) перед отправкой вызывает `Config::load`, так что сам он валидирует.
- **Чем грозит:** сейчас почти ничем. Правило без `float` и без `scratchpad` классифицируется как `Regular`, а `frame` пока никто не читает. Когда T5 начнёт считать кадр через `to_frame`, в Accessibility могут попасть NaN или отрицательные размеры. Новых возможностей атакующему это не даёт: тот же порт уже принимает `keys` с `exec` (см. «Не проверено»).
- **Как чинить (T5):** вызывать `FractionalRect::validated()` там, где кадр применяется, или держать в `Scratchpads` только провалидированные значения. Альтернатива — валидировать `Config` при приёме по IPC. Это решение шире волны, его стоит принять отдельно.
- **Как проверить:** тест T5: правило с `frame = { x = nan, ... }`, собранное в обход `Config::parse`, даёт конечный кадр внутри экрана.

### S3. `launch` из хоткея проверяется только в момент запуска

- **Серьёзность:** замечание
- **Где:** `src/actor/reactor.rs:224-230` (`ToggleScratchpad.launch: Option<String>`), `src/sys/app.rs:75-102`
- **Кто может:** автор конфига, то есть сам пользователь
- **Путь:** `keys` → `ToggleScratchpad { launch }` без проверки при загрузке → (T5) `launch_app(id)` → `validate_bundle_id` → `/usr/bin/open -b id`
- **Чем грозит:** с точки зрения безопасности ничем: единственный сток — `launch_app`, и он проверяет id до создания процесса. Но нарушается принцип «Validate at the boundary» из `CLAUDE.md`: неверный id обнаружится только при нажатии хоткея, причём в виде записи в логе. Пустой `name` в команде тоже не проверяется.
- **Как чинить (T5 или F1):** проверять `launch` при загрузке конфига (сделать `validate_bundle_id` `pub(crate)` и вызывать её из `ConfigPartial::validate` для команд `ToggleScratchpad`). Там же отклонять пустой `name`.
- **Как проверить:** `Config::parse` с `launch = "-a"` или `name = ""` возвращает ошибку. Добавить тест.

### S4. `SpaceId` ↔ `u64` через `transmute` в обход приватного поля

- **Серьёзность:** замечание
- **Где:** `src/sys/space_move.rs:67-76`, `src/sys/screen.rs:20-29`
- **Кто может:** —
- **Чем грозит:** сейчас преобразование корректно: `SpaceId` помечен `#[repr(transparent)]` над `NonZeroU64`, `transmute` проверяет размер при компиляции, а инвариант ненулевого значения сохраняется, потому что вход — `NonZeroU64::new`. Однако код полагается на внутреннее устройство типа из другого модуля. Если `SpaceId` поменяет представление, а размер останется прежним, сборка пройдёт без ошибок. T3 выбрал `transmute`, потому что `screen.rs` в этой задаче был только для чтения.
- **Как чинить (F1 или T6, владелец `screen.rs`):** добавить в `SpaceId` безопасные `pub fn from_raw(u64) -> Option<SpaceId>` и `pub fn get(self) -> u64`, после чего убрать оба `unsafe`. Сейчас `SpaceId::new` существует только под `#[cfg(test)]`.
- **Как проверить:** в `space_move.rs` нет `transmute`, тест `space_id_round_trips` зелёный.

## Проверенное и чистое

- **`launch_app` (`src/sys/app.rs:75-102`):**
  - Shell не используется: `Command::new("/usr/bin/open").args(["-b", &id])`, путь к `open` абсолютный, поэтому подмена через `PATH` невозможна.
  - Проверка разрешает только `[A-Za-z0-9.-]` и отклоняет пустую строку и ведущий `-`. Без ведущего `-` id нельзя принять за флаг `open`. Это ограничение строже контракта (отмечено в отчёте T2) и оправдано, поскольку корректных bundle id оно не отсекает. Тесты `validate_bundle_id_*` покрывают пробел, `;`, `/`, `$(...)`, перевод строки, не-ASCII и `-a`.
  - Права Glide не наследуются. `open -b` просит LaunchServices запустить приложение, и его родителем становится launchd, а не Glide. Поэтому TCC не считает Glide ответственным процессом, и права Accessibility приложению не передаются. Так же работает безопасный режим `exec` (`launch_cli_with_open_at` в `src/sys/bundle.rs`), отличие только в флагах `-n -g -j -W`, которые для scratchpad не нужны. Окружение Glide `open` без `--env` запускаемому приложению не передаёт (поведение `open`, в репозитории не проверялось).
  - Вызов не блокирует: `open` запускается в отдельном потоке, как в `exec_cmd`.
  - В лог попадают только bundle id, код выхода и stderr `open`. Чувствительных данных среди них нет.
- **`set_app_hidden` / `is_app_hidden` / `activate_app`:** процесс ищется через существующий `with_process_id`, который возвращает `Option<Retained<_>>`. Если процесса нет, функции возвращают `None`/`false`, `unwrap` нет, есть тест с `pid_t::MAX`. BOOL возвращается как есть.
- **`spaces_for_window`:** сигнатура `SLSCopySpacesForWindows(int, int, CFArrayRef) -> CFArrayRef` совпадает с yabai. NULL обрабатывается. Возвращённый массив (+1) забирается через `CFRetained::from_raw` без лишнего retain, утечки нет. Элементы без проверки считаются `CFNumber`. Это допущение о приватном API, и живая проверка T3 его подтверждает. Для несуществующего окна функция возвращает `[]` (по отчёту T3).
- **Несуществующий space или окно в `move_window_to_space`:** по отчёту T3, SkyLight такие вызовы молча игнорирует, процесс не падает. `space_id_from_raw(0)` возвращает `None`.
- **Вызов с фонового потока:** по отчёту T3, в живой проверке работает. В `space_move` нет AppKit API, которым нужен главный поток.
- **`FractionalRect::validated` (`src/model/scratchpad.rs`):** NaN превращается в нижнюю границу, `±inf` зажимается в `[0, 1]`, ширина и высота не меньше 0.05, `x + width ≤ 1`. TOML допускает литералы `nan`/`inf`, и они тоже обрабатываются. При загрузке файла функция вызывается из `WindowRule::validated`.
- **`WindowRule::validated`:** правило без действия, пустой `scratchpad`, `scratchpad` с `float = false` и `frame` без `scratchpad` отклоняются с указанием индекса правила. Имя scratchpad ни в какие команды не попадает, это только ключ `BTreeMap`.
- **`ToggleScratchpad` в Reactor:** сейчас команда только пишет `warn!`, строки из неё никуда не передаются.
- **`glide.default.toml`:** пример `toggle_scratchpad` закомментирован, по умолчанию хоткей не включается.
- **`examples/devtool.rs`:** `space move-window` двигает любое окно по wsid. Это инструмент разработчика, в продукт он не попадает. Space id 0 отклоняется.
- **Секреты:** gitleaks по изменённым файлам утечек не нашёл.

## Не проверено

- **IPC-порт Glide в целом (вне волны, существовало до неё).** `Request::UpdateConfig` принимает `Config` от любого локального процесса, который может открыть CFMessagePort, и никак не проверяет отправителя. Такой конфиг может содержать `keys` с `exec`, в том числе в режиме `unsafe_privileged` (`run_unsafe_privileged_exec` → `launch_cli_privileged`, выполнение с правами Glide). Модель доверия порта и доступ к нему (sandbox, имя порта, проверка audit token) я не разбирал. Рекомендую отдельный аудит: если порт доступен любому процессу пользователя, это путь к правам Accessibility Glide, и он важнее всех находок этой волны.
- **Autorelease-пул.** Не проверял, возвращает ли SkyLight внутри `initWithWindows:spaceID:`/`performWithWMBridgeDelegate` autoreleased-объекты. Если да, то при вызове из долгоживущего потока Reactor без `objc2::rc::autoreleasepool` память может расти. В T6 стоит обернуть вызов в `autoreleasepool`, это дёшево.
- **Поведение при полностью включённом SIP и на macOS 26.x:** не проверял ни я, ни T3 (см. его отчёт). Отсюда и S1.
- **Удерживает ли мост асинхронную операцию после `release`:** это внутреннее поведение SkyLight. Живая проверка T3 показала, что перенос выполняется, но статическим анализом я это не подтверждал.
- **Сканеры зависимостей** (`cargo audit`, `osv-scanner`) и `semgrep` не запускались, потому что не установлены. Зависимости в волне не менялись.
- Живые вызовы (`launch_app`, скрытие приложений, перенос окон) я не выполнял по условиям задачи. Тесты тоже не запускал.
