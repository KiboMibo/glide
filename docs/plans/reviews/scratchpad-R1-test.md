## Находки

### 1. Лишние и опечатанные поля `toggle_scratchpad` молча игнорируются — важная

- **Где:** `src/actor/reactor.rs:217-219` (у `ReactorCommand` нет `#[serde(deny_unknown_fields)]`)
- **Воспроизведение:** `"Meta + Alt + K" = { toggle_scratchpad = { name = "k", lanch = "com.x" } }` разбирается без ошибки в `ToggleScratchpad { name: "k", launch: None }`. Проверено временным тестом, в ветку он не вошёл.
- **Чем грозит:** если пользователь опечатается в `launch`, конфиг загрузится, но приложение не будет запускаться. В логе появится только warn «окна нет» (контракт 5.3), а на ошибку в конфиге ничего не укажет.
- **Предлагается:** добавить `#[serde(deny_unknown_fields)]` на вариант или enum `ReactorCommand`. Нужно проверить, что это не ломает разбор untagged `Command`/`WmCommand` (для unit-вариантов атрибут не влияет). Тест на опечатку стоит добавить вместе с исправлением. Сейчас такой тест упал бы, поэтому я его не оставил: это не нарушение явного критерия приёмки.

### 2. Имя scratchpad из одних пробелов принимается — замечание

- **Где:** `src/config.rs:178`
- **Чем грозит:** `scratchpad = "   "` проходит валидацию. Хоткей с `name = "   "` будет работать, но выглядит это как ошибка конфигурации.
- **Предлагается:** проверять `name.trim().is_empty()`. Контракт 5.1 требует только «пустое имя — ошибка», поэтому решение за человеком.

### 3. Два правила с одним именем scratchpad принимаются без предупреждения — замечание (для T5)

- **Где:** `src/config.rs:175-192`
- **Чем грозит:** правила для разных приложений с одним `scratchpad` и разными `frame` проходят валидацию (тест `two_rules_with_the_same_scratchpad_name_are_accepted` фиксирует это как текущее поведение). `Scratchpads::register` оставит окно, которое зарегистрировалось первым, вместе с его `frame`. Какое это окно, зависит от порядка появления окон, а не от порядка правил.
- **Предлагается:** T5 должен решить, что делать: отклонять дубли, предупреждать или брать `frame` первого правила. Если поведение изменится, тест нужно обновить.

### 4. `remove_app` не сбрасывает отложенный показ — замечание

- **Где:** `src/model/scratchpad.rs:108`
- **Чем грозит:** если приложение упало до появления окна, то при следующем появлении окна (например, после ручного запуска через неделю) оно будет показано и получит фокус. Это известное упрощение из раздела 10 плана и отчёта T1. Тест `pending_show_survives_window_registration` фиксирует только сценарий Launch → register.
- **Предлагается:** оставить до T5. Там будет видно, нужен ли сброс по имени приложения.

### 5. `validated` сдвигает `x`/`y` на ε при `x + width = 1` — замечание

- **Где:** `src/model/scratchpad.rs:42-43`
- **Чем грозит:** `{x = 0.2, width = 0.8}` превращается в `x = 0.19999999999999996`, потому что `1.0 - 0.8` в f64 меньше 0.2. На пиксели это не влияет. Но `validated(r) != r` для правильной на вид рамки, и тест с таким значением, сравнивающий результат точно, упадёт.
- **Предлагается:** ничего не менять. Тесты сравнивают такие значения только с результатом того же `validated`.

### 6. `move_window_to_space`/`spaces_for_window` не тестируются без живой системы — замечание

- **Где:** `src/sys/space_move.rs:32-64`
- **Чем грозит:** регрессии в FFI будут видны только на живой машине.
- **Предлагается:** для T6 поставить проверку за трейт или функцию-параметр, чтобы логику Reactor можно было тестировать без SkyLight. Путь «класса нет» (`Unsupported`) на macOS 27 не воспроизводится: класс там есть.

## Допущения

- Скоуп `layout.rs` и `reactor.rs` ограничен кодом T1. Тест Reactor проверяет только, что заглушка ничего не делает. Этот тест нужно будет заменить в T5.
- Уровень находки 1 — «важная», а не «блокирующая»: явный критерий приёмки не нарушен, а опечатка проявляется только при ручной ошибке пользователя. Тест на неё не оставлен красным: он проверял бы поведение, которого контракт не требует.
- Тест `two_rules_with_the_same_scratchpad_name_are_accepted` фиксирует текущее поведение: план про дубли ничего не говорит.
- Для покрытия использован `llvm@22` из Homebrew, а не `cargo-llvm-cov`. Новых зависимостей в проекте нет, служебная сборка шла в отдельный каталог (`CARGO_TARGET_DIR` во временном каталоге сессии).
- В `space_move.rs` тест «нет класса → `Unsupported`» не написан: класс нельзя убрать из рантайма без правки продакшн-кода.
- Мутации проверялись только через `cargo test --lib <модуль>`. Интеграционные тесты не затрагивают код скоупа.
