## Находки

### 1. Важная. Порог для трекпада по умолчанию, вероятно, слишком большой и зависит от ширины экрана

- **Где:** `src/actor/layout.rs:1470` (`step_threshold = W / min(колонок, 3)`), `src/actor/layout.rs:1478` (`delta × sensitivity / 20`).
- **Что не так.** Нужный путь пальцами равен `W / min(колонок, 3) × 20 / scroll_sensitivity` pt. При значениях по умолчанию:

  | Экран (ширина в pt, режим по умолчанию) | 2 колонки | 3+ колонки |
  |---|---|---|
  | MacBook Air 13" (1470) | 735 | 490 |
  | MacBook Pro 14" (1512) | 756 | 504 |
  | MacBook Pro 16" (1728) | 864 | 576 |
  | Внешний 1920 | 960 | 640 |
  | Внешний 5K (2560) | 1280 | 853 |

  Сколько даёт свайп. `kCGScrollWheelEventPointDeltaAxis*` — пиксельные дельты с системным ускорением, без «чанков» ([заметки по CGEvent scroll](https://gist.github.com/svoisen/5215826), [Apple: Handling Trackpad Events](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/HandlingTouchEvents/HandlingTouchEvents.html)). По наблюдениям других проектов, трекпад шлёт обычно меньше 5 pt за событие и 30-50 событий на свайп ([коммит EFL](https://git.enlightenment.org/enlightenment/efl/commit/bd26a126cdcddc4f52379555f66c78bae1e6d2d5.patch), там порог 40 pt на строку). Получается 100-250 pt за спокойный свайп, пока пальцы на трекпаде. Быстрый свайп из-за ускорения даёт больше, но основная часть «пролёта» при быстром свайпе приходится на инерцию, а её T1 правильно отбрасывает. Это оценка по документации и чужим измерениям, не по замеру на macOS 27.
- **Чем грозит.** Спокойный свайп двумя пальцами на MacBook не перелистнёт ни одной колонки. Чтобы перелистнуть, придётся вести пальцами по всему трекпаду быстро или несколько раз. На широком внешнем мониторе ещё хуже, хотя трекпад тот же. Цель плана «один свайп примерно на ширину колонки — одна колонка» формально выполнена (путь равен ширине шага в pt), но по ощущениям пользователя, скорее всего, нет.
- **Что предлагается (для F1, после замера).**
  1. Предпочтительно: не привязывать порог трекпада к ширине экрана, потому что путь пальцев не зависит от монитора. Для continuous-событий порог = `TRACKPAD_COLUMN_SWIPE_PT × 20 / scroll_sensitivity`, где `TRACKPAD_COLUMN_SWIPE_PT ≈ 250`. Тогда при 20 нужно ≈ 250 pt, при 40 ≈ 125 pt, на любом экране. Если порог станет меньше ширины колонки, накопление через `accumulate_scroll(delta, threshold)` не меняется: достаточно передать другой порог в ветке `continuous`.
  2. Если формулу оставить: поднять `scroll_sensitivity` по умолчанию до ≈ 70 (1512 / 2 × 20 / 70 ≈ 216 pt, 1920 / 2 × 20 / 70 ≈ 274 pt). Минус: та же настройка масштабирует «быстрое» колесо (ветка `|delta| ≥ 10` строк в `layout.rs:1480`), и при сильной прокрутке колесом шагов станет больше.
  3. Число откалибровать по записи: человек записывает трассу (сценарий Ж1) и суммирует `delta_x` у событий `phase: Changed` одного удобного свайпа. Медиану по 5-10 свайпам взять за `TRACKPAD_COLUMN_SWIPE_PT`.

### 2. Важная. Приложение под курсором получает тот же свайп

- **Где:** `src/actor/mouse.rs:91` (`CGEventTapOptions::ListenOnly`).
- **Что не так.** Glide только читает события прокрутки и не поглощает их. Для колеса так было и раньше. Горизонтальный свайп двумя пальцами в браузерах и Finder — это ещё и «Смахивание между страницами» (назад/вперёд) или горизонтальная прокрутка. Будут ли они срабатывать при зажатом модификаторе, зависит от приложения. Проверить можно только вживую.
- **Чем грозит.** Пользователь листает колонку, а Safari или Chrome заодно уходит на предыдущую страницу, или таблица под курсором уезжает вбок.
- **Что предлагается.** Проверить сценарием Ж4. Если мешает, в F1 или отдельной задаче рассмотреть tap с `Default` и возврат `None` для обработанных событий прокрутки. Это меняет архитектуру `mouse.rs` (решение прямо в callback tap'а), поэтому лучше решать отдельно. Пока в `glide.default.toml` записано, что приложение тоже получает события.

### 3. Замечание. Незавершённый прогресс переживает жест без модификатора

- **Где:** `src/actor/reactor.rs:968` (проверка модификатора до вызова `handle_scroll_wheel`), `src/actor/layout.rs:1491`.
- **Что не так.** `Began` сбрасывает прогресс только если модификатор зажат в момент `Began`. Прогресс не сбрасывается ни на `Ended`, ни при отпускании модификатора. Сценарий: с Option провести 90% шага, отпустить пальцы; следующий жест начать без Option и зажать Option посередине. Первое же небольшое движение перелистнёт колонку.
- **Чем грозит.** Редкий «беспричинный» шаг. Состояние не портится.
- **Что предлагается.** Сбрасывать прогресс и на `Ended`, или передавать события с фазой `Began`/`Ended` в LayoutManager независимо от модификатора (только для сброса).

### 4. Замечание. Вертикальные дельты подмешиваются в горизонтальный свайп

- **Где:** `src/actor/reactor.rs:973` (`if delta_x != 0.0 { delta_x } else { delta_y }`).
- **Что не так.** Для трекпада события почти горизонтального свайпа иногда приходят с `delta_x = 0` и небольшой `delta_y`. Они добавляются в тот же накопитель со своим знаком. Вертикальный свайп с модификатором тоже листает колонки. Это старое поведение, T1 его отметил.
- **Чем грозит.** Небольшой дрейф порога. Для пользователей, у которых Option + вертикальная прокрутка что-то значит в приложениях, колонки будут листаться неожиданно.
- **Что предлагается.** Для continuous-событий брать только `delta_x`, либо ось с большей абсолютной суммой за жест. Решить после живой проверки (Ж3).

### 5. Замечание. Мыши с «плавной» прокруткой пойдут по пиксельной ветке

- **Где:** `src/actor/mouse.rs:188-203`.
- **Что не так.** Magic Mouse и мыши с утилитами плавной прокрутки (Mos, Logi Options+ smooth scrolling, SmoothScroll) шлют события с `IS_CONTINUOUS = 1`. Для них одно деление больше не равно одной колонке: нужен путь в pt, как на трекпаде. Критерий 3 про обычное колесо выполнен.
- **Чем грозит.** У части пользователей мышь начнёт листать «медленнее».
- **Что предлагается.** Упомянуть в release notes. Проверить сценарием Ж6, если есть такая мышь.

### 6. Замечание. Неточное описание порога в `glide.default.toml` (исправлено)

- **Где:** `glide.default.toml`, `scroll_sensitivity`.
- **Что было.** «At 20.0, a trackpad swipe of about one column width moves one column». На деле шаг — `ширина экрана / min(колонок, 3)`, а не ширина колонки (при двух колонках шириной 1/3 шаг равен половине экрана). Ещё не было сказано, что 0 выключает трекпад, что инерция не учитывается и что приложение тоже получает событие.
- **Сделано.** Описание переписано, см. ниже.

## Изменения в документации

Коммит `8be230c docs: Describe the trackpad scroll threshold and modifier in the default config`.

- `glide.default.toml`:
  - `scroll.scroll_sensitivity`: диапазон 0-100 (как в `validated()`), формула пути для трекпада, пример 960 pt для 1920 pt и 2 колонок, «при 40 вдвое короче», 0 выключает трекпад, инерция не листает, деление колеса — одна колонка независимо от значения.
  - `scroll.invert_scroll_direction`: действует и на трекпад, и на колесо.
  - `scroll.scroll_modifier`: значения, жест — модификатор + свайп двумя пальцами по трекпаду или колесо; другие модификаторы не мешают; приложение под курсором тоже получает события.
  - Разбор проверен: `cargo test --lib config` — 53 passed.
- `README.md`: раздела про скролл-раскладку нет, не менялся.
- `ARCHITECTURE.md`, раздел «Scroll layout»: вне списка разрешённых файлов. Устаревших утверждений о прокрутке колесом там нет.

## Сценарии живой проверки (для человека)

Подготовка. Собрать ветку `wave/scroll-trackpad-w1` и запустить Glide с записью:
```bash
RUST_LOG=info,glide_wm::actor::reactor=debug cargo run -- --record traces/trace-$(date +%Y%m%d-%H%M%S).ron
```
В конфиге: `settings.experimental.scroll.enable = true`, скролл-раскладка на текущем пространстве, 4-5 окон (например, Terminal, TextEdit, Finder, Safari, Notes), по умолчанию `visible_columns = 2`. Записать модель Mac, ширину экрана в pt («Системные настройки → Дисплеи», «Выглядит как …») и включена ли «Естественная прокрутка».

При любом провале приложить: трассу `traces/trace-*.ron`, лог терминала, номер сценария, что делали (скорость и длина свайпа, сколько пальцев, какой модификатор), что ожидали и что увидели, ширину экрана и число колонок. По возможности — запись экрана (Cmd+Shift+5).

| # | Шаги | Ожидаемо |
|---|------|----------|
| Ж1. Калибровка порога | Зажать Option, 10 раз спокойно провести двумя пальцами справа налево примерно на половину трекпада, между свайпами отрывать пальцы. Потом 5 раз на весь трекпад. | Каждый свайп — не больше одной колонки, без пролёта после отрыва пальцев. Если полусвайп ничего не листает — это находка 1, приложить трассу: по ней считаем сумму `delta_x` на свайп. |
| Ж2. Инерция | Option + быстрый короткий «бросок» двумя пальцами. | Не больше одной колонки. Колонки не листаются, пока идёт инерция. |
| Ж3. Направление и оси | Option + свайп справа налево, потом слева направо. Затем Option + вертикальный свайп. | С включённой естественной прокруткой при свайпе влево открывается колонка справа (содержимое идёт за пальцами). Записать, листает ли вертикальный свайп (ожидаемо да, находка 4). |
